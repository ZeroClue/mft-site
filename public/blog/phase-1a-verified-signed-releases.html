MFTPlus Phase 1A: Verified, Signed, and Audited Releases

If you run infrastructure software, “download the binary” is the most dangerous sentence in the docs. You are trusting a file from the internet to run with elevated privileges on a machine that moves your company’s data. Phase 1A is our first hardening wave aimed squarely at that moment: making every MFTPlus release something you can independently verify, not something you have to take on faith.

This release wave is about trust at the distribution layer. It does not change how transfers work. It changes how you know the software you installed is the software we built.

What shipped in Phase 1A

Checksums and SBOMs on every release

Every release artifact now ships alongside a SHA256SUMS file and a software bill of materials (SBOM). The checksum lets you confirm the bytes were not altered in transit. The SBOM lists exactly what is in the build, so your security team can scan it against known vulnerabilities before it touches a production host.

Signed releases with minisign

Checksums prove integrity. Signatures prove provenance. We now sign release artifacts with minisign, using an offline release-signing key. A signature means the file came from us — not from a compromised mirror, a poisoned CDN, or a typo-squatted download.

A published release-signing public key

You should not have to trust a key that only lives on our website. We’ve published our release-signing public key and copy-paste verification snippets at docs.mftplus.co.za/install/verify. Pin it once, and you can verify every future release against the same key.

A verification guide that assumes you’re busy

A public key with no instructions is a rock with a map painted on it. Our Verifying Releases guide walks through checksum, signature, and SBOM checks step by step, with the exact commands for Linux, macOS, and Windows.

Verification built into the install path

The one-line install script now supports --verify, and our install docs explain how to confirm what you’re about to run before you run it. Verification is no longer a separate, optional chore — it’s part of the same motion as installing.

Trust signals, on the site. The landing page now states our distribution guarantees up front: checksums, SBOMs, and signed releases. If a download page can’t tell you how to verify what it hands you, that’s a red flag. Ours does.

The security sweep behind it

Phase 1A also closed the gaps that make “verify your downloads” a joke if the build server itself is compromised. Alongside the distribution work:

  • No more hardcoded fallback secrets. Production code now fails closed instead of silently using a known default key when an environment variable is missing.
  • Secrets rotation runbook. A documented, repeatable procedure for rotating production credentials, with the failure modes called out explicitly.
  • Hardened 2FA at rest. Two-factor recovery codes are now hashed, and TOTP encryption requires a real key in production.
  • Security scanning in CI. Static analysis, secret scanning, and dependency auditing now run on every build, so a regression can’t ship quietly.

None of this is glamorous. All of it is the difference between “we think we’re secure” and “we can prove the chain held.”

How to verify a download

From the Verifying Releases guide, the short version:

# 1. Fetch the release, its checksum, and its signature
curl -O https://releases.mftplus.co.za/vX.Y.Z/mftctl-linux-amd64
curl -O https://releases.mftplus.co.za/vX.Y.Z/SHA256SUMS
curl -O https://releases.mftplus.co.za/vX.Y.Z/SHA256SUMS.sig

# 2. Verify the signature against our published public key
minisign -Vm SHA256SUMS -P <our-public-key>

# 3. Confirm your binary matches the verified checksum
sha256sum -c SHA256SUMS

The full commands, the exact public key to pin, and the Windows/macOS variants are in the guide. Copy-paste snippets live at docs.mftplus.co.za/install/verify.

FAQ

What is a SHA256SUMS file?

It’s a list of filenames and their SHA-256 hashes. After downloading, you compute the hash of your file and compare it to the listed value. If they match, the bytes you received are byte-for-byte identical to what we published — nothing altered them in transit.

What does signing add that a checksum doesn’t?

A checksum proves the file wasn’t changed. It does not prove who created it. A minisign signature proves the file was signed by the holder of our release key. Together they answer two questions: “is this intact?” and “did it come from us?”

Where do I get the public key?

At docs.mftplus.co.za/install/verify, along with the exact minisign command to verify a release. Pin the key in your own tooling so future releases verify against the same one.

Do I need minisign installed?

Only for the signature step. minisign is a small, dependency-free tool available for Linux, macOS, and Windows. The checksum step uses sha256sum (or CertUtil on Windows), which is already on most systems.

Does this change how transfers work?

No. Phase 1A is entirely about how you obtain and trust the MFTPlus software. Transfer behaviour, encryption, and the audit chain are unchanged by this release wave.

What if verification fails?

Do not run the file. Re-download from the official release host, and if it still fails, report it. A failed signature means the artifact was not signed by our release key — treat that as a potential compromise, not an inconvenience.
